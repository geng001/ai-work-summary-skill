- 正式 Skill 名称和显式调用名称：`ai-work-summary-skill`
- 适用版本：首版 MVP
- 契约日期：2026-09-28
- 契约状态：已人工确认

- 本契约只定义产品行为，不规定非必要的框架、脚本或实现结构。

## 2. 目标与非目标

### 2.1 目标

让用户通过明确调用 Codex Skill，将当前任务和明确指定材料中的实际工作结果转换为可信、可追溯、可增量更新的 Markdown：

```text
独立工作记录
→ 当日日报或增量更新
→ 周报或增量更新
```

Skill 必须：

- 按工作目标聚合，而不是机械罗列文件、会话或提交；
- 在用户明确要求时，从当前可见会话补齐指定日期缺失的工作记录，且不因此生成日报；
- 保留 `work_id`、产出物、证据、验证、状态、风险和后续动作；
- 区分事实、AI 推断、建议、人工补充和待确认信息；
- 在没有完成证据时避免把工作标记为 `COMPLETED`；
- 重复运行时避免重复事项和无意义写回；
- 只在明确授权范围内读取和写入；
- 保护人工编辑区域。

### 2.2 非目标

首版不负责：

- 为 Codex 之外的平台提供可安装、可执行的 Skill；
- 建设桌面应用、Web 平台、账号、团队权限、数据库或云同步；
- 自动扫描 Codex 或其他 AI 的历史私有会话，包括以“补录今天全部工作”为理由打开其他会话；
- 在一次指定日期的批量补录中改写多个日期，或在用户已指定单一项目时顺带记录其他项目；
- 批量补录工作记录后自动继续生成日报或周报；
- 全局监控屏幕、窗口、浏览器、键盘、文件活动或使用时长；
- 后台常驻或定时生成日报、周报；
- 多个 AI 并发改写同一篇日报或周报；
- 自动发送邮件、企业微信、飞书或其他外部消息；
- 团队绩效、工时统计、排行榜或生产力评分；
- 根据文件数、提交数、聊天数或使用时长直接判断工作完成；
- 自动迁移、接管或覆盖不符合本契约标记协议的历史日报和周报。

## 3. 调用与触发边界

### 3.1 触发条件

首版只在用户明确调用 Skill 并表达下列动作之一时执行：

1. 记录当前任务；
2. 生成或更新指定日期的日报；
3. 生成或更新指定周的周报；
4. 按指定日期批量补录当前可见会话中的工作记录。

一次调用只执行其中一个动作。用户同时提出多个动作时，停止并请求其指定一个动作。“记录当前任务”只处理一个当前工作目标，不得改写成第 4 个动作。

Skill 可以在合适时机建议用户调用，但建议不构成读取或写入授权，也不得自动执行。

### 3.2 典型触发示例

- “调用工作总结 Skill，记录本次任务。”
- “调用工作总结 Skill，把本次工作记录写入 `D:\notes\work-summary`。”
- “根据 `D:\notes\work-summary` 中 2026-09-28 的工作记录生成日报。”
- “增量更新 2026-09-28 的日报，保留人工内容。”
- “根据本周日报、原始工作记录和人工补充生成周报。”
- “使用 `$ai-work-summary-skill` 生成包含 2026-10-08 的周报。”
- “使用我提供的单个会话导出文件补充一条工作记录。”
- “使用 `$ai-work-summary-skill` 补录当前会话中 2026-10-10 的工作记录。”
- “使用 `$ai-work-summary-skill` 补录当前会话中 2026-10-10 的工作记录。项目：Spec-Kit。”

### 3.3 不应触发示例

- 用户只要求总结一篇文章、一个网页或一段普通文本；
- 用户只要求解释代码、排查问题或完成开发任务，没有明确要求记录工作；
- 用户泛泛询问“今天做了什么”，但没有调用 Skill 或授权读取记录；
- 用户要求扫描所有历史会话、监控电脑活动或评价员工绩效；
- 用户要求直接发送日报、周报到外部平台；
- 用户要求修改不属于本 Skill 管理且没有明确授权的历史报告；
- 用户要求扫描其他历史会话、整个项目或其他日期的记录来补齐某一天的工作；
- 用户只说“记录当前任务”，但当前会话里还有其他工作目标。此时仍只记录当前这一个目标。

## 4. 工作目录与文件协议

### 4.1 工作总结根目录解析

定义 `work_summary_root`：

1. 用户调用时明确指定工作总结目录：直接使用该目录作为 `work_summary_root`；
2. 用户未指定时：使用当前打开项目根目录下的 `work-summary/`；
3. 无法可靠确定当前项目根目录、目标目录不可写，或存在多个候选目录时：停止并请求用户指定；
4. 输出目录只代表本次动作的输出和受管文件范围，不自动授权读取该目录中的其他任意材料。

### 4.2 固定目录和命名规则

```text
<work_summary_root>/
├── 工作记录/
│   └── YYYY/MM/DD/
│       └── wrk_<UUIDv7>.md
├── 日报/
│   └── YYYY/MM/
│       └── YYYY-MM-DD 工作日报.md
└── 周报/
    └── YYYY/MM/
        └── YYYY-Www（MM月DD日-MM月DD日）工作周报.md
```

规则：

- 日期和时间按 `Asia/Shanghai` 解释；
- 一周为周一至周日，使用 ISO 周编号；
- 周报保存在该周起始日所在月份；
- 跨月周仍只生成一份周报，文件名必须显示实际起止日期；
- 日报必须保存 `week_id` 和对应周报路径；
- 周报必须保存 `period_start`、`period_end` 和来源日报路径；
- 文件标题变化不得导致工作记录文件重命名。
- YAML 日期使用 `YYYY-MM-DD`；工作记录在有可支撑的发生时刻时，`time` 使用 `HH:MM:SS+08:00`，没有可支撑的时刻时省略 `time`；`created_at`、`updated_at` 和 `generated_at` 使用包含时区的 RFC 3339 时间戳；
- `+08:00` 和 RFC 3339 中的 `T` 属于机器层时间语义，不因 Obsidian 的本地化显示或用户可读格式而删除；已省略的 `time` 不得用 `00:00:00` 或虚构时刻代替；
- AI 托管正文中的人类可读时间使用 `YYYY-MM-DD HH:MM:SS（北京时间）`，并从对应 YAML 时间字段派生。工作记录省略 `time` 时，记录摘要写“时刻未记录”，不显示钟点。

### 4.3 `work_id`

- 新工作记录使用 `wrk_<UUIDv7>`；
- `work_id` 在首次创建时生成，之后永久保留；
- `work_id` 不从标题、内容、文件路径或项目名称重新计算；
- 更新现有记录时必须沿用原 `work_id`；
- 两个文件出现相同 `work_id` 且内容或来源不一致时视为冲突，停止相关合并；
- 无法唯一判断是否为已有记录时，不静默复用或生成替代 ID，应请求用户确认。
- `work_id` 用于唯一标识，并可按 UUIDv7 的时间部分大致反映生成先后；它不表示任务优先级，不得改为依赖全局计数器的顺序号，也不得从其数值推断业务优先级。

### 4.4 AI 托管区和人工区

受管 Markdown 使用以下边界：

```markdown
<!-- AI-MANAGED:START -->
AI 可以生成或重新生成的内容
<!-- AI-MANAGED:END -->

<!-- HUMAN:START -->
用户编辑和补充内容
<!-- HUMAN:END -->
```

更新规则：

- Skill 只允许更新预先声明的系统 YAML 属性和 `AI-MANAGED` 区域；
- `HUMAN` 区域及其他未声明人工内容不得被删除、覆盖或改写；
- 用户直接修改 `AI-MANAGED` 区域的内容，后续生成可能覆盖；文件中应明确提示这一点；
- 开始或结束标记缺失、重复、嵌套或顺序错误时停止写入并报告；
- 不符合标记协议的已有文件不得被自动接管或整体覆盖；
- 内容和系统属性没有变化时不得写回文件。

## 5. 输入与输出

### 默认语言

- 首版默认面向中文使用场景，Skill 的用户可见界面文案，以及工作记录、日报和周报的标题、栏目名称与 AI 生成叙述，默认使用简体中文；
- 本契约已经固定的英文状态值、YAML 字段名、`work_id`、受管区标记及其他机器可识别标识保持不变，不因默认语言规则而翻译或改名。
- YAML frontmatter 是机器层；AI 托管正文是展示层。正文必须以有实际含义的中文一级标题开头，不得仅使用 `work_id` 作为标题；
- 工作记录正文必须包含“记录摘要”，日报和周报正文必须包含“报告摘要”。摘要中的中文文档类型、工作类型、状态和人类可读时间必须从同一份 YAML 派生，且保留对应英文枚举值以便追溯；
- 中文展示映射固定为：文档类型 `work_record`→工作记录、`daily_report`→工作日报、`weekly_report`→工作周报；状态 `COMPLETED`→已完成、`IN_PROGRESS`→进行中、`BLOCKED`→已阻塞、`PENDING_CONFIRMATION`→待确认、`UNVERIFIED`→未验证；工作类型 `requirements`→需求分析、`development`→开发实现、`documentation`→文档整理、`presentation`→演示与汇报、`environment`→环境配置、`research`→调研分析、`collaboration`→协作沟通、`support`→支持与排障。

### 5.1 记录当前任务

允许输入：

- 当前任务中已经可见的会话上下文；
- 用户在本次调用中明确指定的文件或目录；
- 用户显式提供的单个会话导出材料；
- 用户明确提供的项目名、工作目标、补充事实和验证结论。

每份工作记录至少包含：

```text
work_id
日期和时间
工作目标
工作类型
所属项目
来源 AI 和来源说明
实际完成
主要产出物
关键结论和决定
验证或审阅结果
当前状态
未完成、风险和阻断
后续动作
证据路径或链接
```

状态只允许：

```text
COMPLETED
IN_PROGRESS
BLOCKED
PENDING_CONFIRMATION
UNVERIFIED
```

### 5.2 生成或更新日报

输入范围：

- 指定日期下的受管工作记录；
- 已存在的同日日报；
- 日报中的人工区域；
- 用户本次明确指定的补充材料。

日报至少包含：

- 今日结论；
- 按工作目标聚合的工作事项；
- 重要决定；
- 主要产出物和验证结果；
- 阻断、风险和待确认事项；
- 后续计划；
- 人工补充区域；
- 来源 `work_id` 和对应周报信息。

### 5.3 生成或更新周报

用户用一个日期指定这一周，不需要提供 `YYYY-Www`。该日期所在的周一至周日就是报告周期；`week_id`、起止日期和文件路径由 `paths` 从该日期算出。用户只给出周编号时也可以使用。日期和周编号指向不同周，或两者都没有时，停止并请求一个日期。“本周”指 `Asia/Shanghai` 的今天所在周。

输入范围：

- 指定周内的日报；
- 对应原始工作记录；
- 日报和周报中的人工区域；
- 用户本次明确指定的补充材料。

周报至少包含：

- 本周结论；
- 按工作目标聚合的重点工作；
- 主要产出物和验证结果；
- 重要决定；
- 能力或环境建设；
- 结转事项、风险和阻断；
- 下周计划；
- 人工补充区域；
- 覆盖日期、来源日报和来源 `work_id`。

### 5.4 材料不足时的行为

- 有足够事实描述工作，但缺少完成证据：可以创建记录，状态使用 `UNVERIFIED`，并明确缺失证据；
- 工作仍在进行：使用 `IN_PROGRESS`，不得为了形成日报而提升状态；
- 目标、日期、输出目录或记录身份无法可靠确定：停止写入并请求必要信息；
- 指定日期没有工作记录：不创建看似正常的空日报，报告没有可用来源；
- 指定周没有日报、工作记录或人工补充：不创建看似正常的空周报；
- 指定日期的批量补录没有可归档的工作目标：不创建空工作记录，并报告未记录项；
- 部分材料缺失但其余材料仍可安全汇总：明确列出缺口，不静默忽略或补造；
- 无法确认跨会话内容是否属于同一工作目标：保持分开或请求用户确认，不强行合并。

### 5.5 按指定日期批量补录当前可见会话的工作记录

这个动作补齐指定日期缺失的工作记录。它不生成日报或周报。

允许输入：

- 当前会话中模型实际可见的上下文；
- 用户在本次调用中明确提供的材料；
- 指定日期目录 `工作记录/YYYY/MM/DD/` 中已有的受管 `wrk_*.md`，且仅用于去重和更新。

必须拒绝的读取：

- 其他历史会话；
- 未在本次调用中明确授权的聊天记录；
- 为寻找额外证据而扫描项目目录；
- 其他日期的工作记录、日报或周报；
- 仅因会话文本提到就打开的路径、链接或旧总结。

日期是工作发生日期，不是内容被提到的日期。只纳入有明确日期依据，或能从当前会话时序可靠判断为该日实际发生的工作。历史背景、旧文档、以前的工作总结、摘要中的过去事项、被引用的历史工作，以及只用于解释当前问题的旧实现，不得因出现在上下文中就归入指定日期。日期无法可靠判断时，不归档，并列入未记录项。日期可靠但没有可支撑的发生时刻时，仍然建记录并省略 `time`；不得写成 `00:00:00`、本次补录的执行时间，或把 `created_at` 抄进 `time`。记录摘要写“时刻未记录”。更新已有记录时，保留已有且有依据的 `time`。

归档单位是独立工作目标。同一目标的多轮分析、修改和验证合并为一条记录；不同目标分别记录；无法确认是否同一目标时保持分开。纯闲聊、重复表达和没有工作含义的内容不记录。不得把多个无关目标合成一条记录。

创建前必须先读取该日已有受管记录：

- 已有记录的目标、项目和内容能够可靠确认是同一工作目标时，复用该文件并保持原 `work_id`；
- 明显是不同目标时，创建新的普通工作记录；
- 一个目标可能对应多条已有记录，或两个目标可能对应同一条已有记录时，不合并、不覆盖、不另建竞争记录，并把该事项标为待确认；
- 不得用关键词、相同文件、相同工作类型或模糊文本相似度强行合并。

用户在本次调用中指定单一项目时，只记录明确属于该项目的目标。其他项目不纳入。未指定项目时，可以分别为归属明确的不同项目写记录；归属不明确的事项不归类。本动作不提供“一次调用忽略项目过滤并跨项目全量补录”的模式。

每条接受的目标使用现有工作记录协议，不新增字段。没有事实支撑的产出物、决定或风险不写占位内容。状态规则与第 5.1 和 5.4 节相同：分析结论、方案、提示词修改、AI 声称完成或文件存在，都不足以标记 `COMPLETED`。有足够事实描述工作但缺少完成证据时，仍写入非完成状态；事实本身不足时不建记录，原因记为证据不足。

该日受管文件标记损坏，或出现冲突的重复 `work_id` 时，在任何写入之前停止整个补录。

完成后报告：指定日期、指定项目、识别出的独立目标数、新建记录、复用或更新的记录、跳过项及原因。跳过原因只使用：日期无法确认、项目归属不明、不属于指定项目、与已有记录是否重复存在歧义、证据不足、非工作内容。然后停止，不自动生成日报。

## 6. 读取、写入、外发和人工确认边界

### 6.1 读取边界

- 可以使用当前任务已经可见的上下文；
- 可以读取用户本次明确指定的文件和目录；
- 执行更新、去重和汇总时，可以读取 `work_summary_root` 内与目标日期、目标周和相关 `work_id` 直接有关的受管文件；
- 按指定日期批量补录时，受管读取只限该日 `工作记录/YYYY/MM/DD/wrk_*.md`；不得借此读取日报、周报或其他日期；
- 不得因为当前打开了某个项目，就自动遍历整个项目；
- 不得搜索其他历史私有会话；
- 不得把输出目录解释为读取其中所有文件的授权；
- 需要扩大读取范围时，先说明原因、目标路径和用途，并等待用户确认。

### 6.2 写入边界

- 只写入解析后的 `work_summary_root`；
- 只创建或更新本契约定义的工作记录、日报和周报；
- 对已有受管报告只更新系统属性和 `AI-MANAGED` 区域；
- 不修改源代码、需求文档、原始证据或用户指定材料；
- 不删除历史记录，不自动迁移旧报告，不创建范围外索引或数据库；
- 任何覆盖风险无法排除时停止写入。

### 6.3 外发边界

- 首版不自动上传、同步、发送或发布任何材料；
- 不调用外部消息、邮件、协作或存储平台；
- 用户要求外发时，视为独立动作并重新确认目标、内容和授权，本 Skill 本身不执行。

### 6.4 必须人工确认的情况

- 扩大读取或写入范围；
- 接管或迁移无受管标记的历史日报、周报；
- 多条记录是否属于同一工作目标存在实质歧义；
- 相同 `work_id` 出现冲突；
- 事实来源冲突会影响完成状态或关键结论；
- 标记损坏，需要重建文件结构；
- 用户请求删除、覆盖、发送、发布或批量迁移内容。

## 7. 信息类型和证据规则

### 7.1 事实

事实必须来自以下至少一种来源：

- 用户明确陈述；
- 当前任务中可见的真实工具或命令结果；
- 用户明确指定文件中的实际内容；
- 可定位的产出物、测试、构建、渲染、审阅或决定记录。

文件存在、文件发生修改、出现 Git 提交或 AI 声称完成，都不能单独证明业务目标已经完成。

### 7.2 AI 推断

- AI 根据材料归纳但未被直接确认的内容必须标记为“AI 推断”；
- AI 推断不能作为 `COMPLETED` 的唯一依据；
- 推断会影响工作目标归并、状态或关键结论时，转为 `PENDING_CONFIRMATION`。

### 7.3 建议

- 建议只进入“后续动作”“风险应对”或明确的建议区域；
- 建议不得写成已经决定、已经执行或已经完成的事实。

### 7.4 人工补充

- 用户补充的会议、沟通、线下支持等内容标记为人工来源；
- 人工补充可以作为用户确认事实，但不能伪装成自动验证结果；
- 后续汇总必须保留其来源属性和人工区域内容。

### 7.5 待确认信息

以下内容使用 `PENDING_CONFIRMATION` 或明确的待确认标识：

- 来源互相冲突；
- 工作目标归并不确定；
- 用户尚未确认的重要决定；
- 证据不足且不能安全判断当前状态。

## 8. 重复运行、冲突、失败和停止条件

### 8.1 重复运行

- 工作记录以稳定 `work_id` 标识；
- 日报按来源 `work_id` 聚合，不因重复运行重复新增同一事项；
- 周报按来源日报和 `work_id` 去重，不机械复制日报；
- 受管源内容和系统属性没有变化时跳过写入；
- 源记录发生变化时可以重新生成整个 `AI-MANAGED` 区域，但必须保留 `HUMAN` 区域；
- 更新现有工作记录必须由明确路径、明确 `work_id` 或其他无歧义证据定位；无法定位时请求确认。第 5.5 节的同日目标去重只适用于“按指定日期批量补录”，不放宽“记录当前任务”的定位要求。

### 8.2 冲突处理

- 相同 `work_id` 对应不同记录：停止相关合并；
- 同一事实存在冲突：列出各来源，不静默选择；
- 完成状态冲突：采用非完成状态并请求确认，不向 `COMPLETED` 乐观升级；
- 工作目标归并冲突：保持独立事项或请求确认；按指定日期批量补录时，若歧义发生在与当日已有记录之间，不新建竞争记录，适用第 5.5 节；
- 人工内容与 AI 结论冲突：保留人工原文，标记冲突，不覆盖人工内容；
- 路径规则与已有受管文件冲突：停止并报告候选文件。

### 8.3 失败行为

- 写入前无法确认目标路径：不写入；
- 读取失败：说明具体路径和影响，不把缺失材料视为空内容；
- 标记协议损坏：不重写整篇文件；
- YAML 无法安全解析或存在重复关键属性：不修改文件；
- 部分文件写入失败：报告已成功和未成功的文件，不宣称整体完成；
- 无法验证输出是否保存成功：结果标记为 `UNVERIFIED`。

### 8.4 停止条件

出现以下任一情况时停止相关写入并请求用户处理：

- 需要未经授权的读取、写入或外发；
- 目标目录不明确或不可写；
- 即将覆盖无法识别的人工内容；
- 受管标记或关键 YAML 结构异常；
- 相同 `work_id` 冲突；
- 关键事实冲突会改变状态或结论；
- 用户要求的行为已经超出首版非目标；
- 批量补录缺少唯一日期，或该日受管记录无法安全去重。

## 9. 行为验收场景

### AC-001｜使用默认目录记录当前任务

**给定**：用户在可识别的当前项目中明确调用“记录当前任务”，没有指定输出目录，当前上下文包含目标、实际产出和验证证据。

**预期**：在 `<当前项目根目录>/work-summary/工作记录/YYYY/MM/DD/` 创建一份 `wrk_<UUIDv7>.md`；字段完整；正文使用有实际含义的中文标题，并包含与 YAML 一致的中文记录摘要；有充分完成证据时可以标记 `COMPLETED`；不读取其他历史会话。

### AC-002｜缺少完成证据

**给定**：当前上下文说明进行了某项工作，但没有测试、审阅、产出物或用户确认能够证明完成。

**预期**：允许生成工作记录，但状态为 `UNVERIFIED` 或符合事实的非完成状态；明确缺少的证据；不得写成已完成。

### AC-003｜首次生成日报并按目标聚合

**给定**：指定日期存在多份不同工作类型的记录，其中部分记录属于同一工作目标。

**预期**：生成一篇按工作目标组织的日报；正文包含与 YAML 一致的中文报告摘要；同一目标合理聚合；每个事项保留来源 `work_id`；未经验证事项不升级为完成。

### AC-004｜日报重复运行和增量更新

**给定**：日报已经存在并包含人工区域；先在源记录无变化时重复运行，再新增或修改一份工作记录。

**预期**：第一次不产生重复事项且不写回无变化文件；第二次重新生成必要的 AI 托管内容；新增、变化和未变化来源处理正确；人工区域逐字保留。

### AC-005｜生成跨月周报

**给定**：目标周为 2026-W40，周期是 2026-09-28 至 2026-10-04，日报跨越 9 月和 10 月。

**预期**：只生成一份 `周报/2026/09/2026-W40（09月28日-10月04日）工作周报.md`；正文包含与 YAML 一致的中文报告摘要；周报记录完整周期及所有来源日报；各日报记录 `week_id` 和对应周报路径。

### AC-006｜读取范围受限

**给定**：用户指定一个输出目录和两份输入文件，项目中还有其他未授权文件。

**预期**：只读取当前可见上下文、两份指定文件以及更新所必需的相关受管输出；不遍历项目或历史会话；输出不包含范围外内容。

### AC-007｜人工区域和标记异常

**给定**：一篇日报包含有效 `HUMAN` 内容，另一篇日报缺少 `AI-MANAGED:END` 标记。

**预期**：前者更新后完整保留人工内容；后者停止写入并报告标记异常，不尝试整体重建或覆盖。

### AC-008｜来源冲突和重复 ID

**给定**：两份记录使用相同 `work_id` 但内容不同，或者同一事项的完成状态互相冲突。

**预期**：停止合并重复 ID；状态冲突不向 `COMPLETED` 升级；列出来源和需要人工确认的问题。

### AC-009｜批量补录识别多个独立目标

**给定**：用户明确调用“补录当前可见会话中 2026-10-10 的工作记录”。当前可见上下文里有两个互不隶属的工作目标，都能从会话时序可靠判断发生在该日，且该日没有已有受管记录。

**预期**：创建两份普通工作记录，各用自己的 `work_id`；不合成一份；不生成日报或周报；不读取其他会话。

### AC-010｜同一目标的多轮归并

**给定**：同一指定日期的可见会话中，问题分析、提示词调整、规则澄清和职责讨论都指向同一个工作目标。

**预期**：只创建或更新一条工作记录，不按消息、文件或工具调用拆开。

### AC-011｜复用当日已有记录

**给定**：指定日期已有一条受管记录，其目标、项目和内容与当前会话中的一个目标可靠对应；会话中另有一个明显不同的目标。

**预期**：前一个目标复用原 `work_id` 更新，不新建；后一个目标新建。人工区域逐字保留。相似措辞但不是同一目标时不得复用。

### AC-012｜日期无法确认时不归档

**给定**：可见上下文中有一项工作，但无法判断它是否发生在指定日期。

**预期**：不为该项创建记录；完成报告将其列为未记录，原因是日期无法确认。

### AC-020｜日期可靠但没有发生时刻时仍记录

**给定**：一项工作能够可靠判断发生在指定日期，但可见上下文没有可支撑的钟点。

**预期**：创建工作记录，省略 `time`；记录摘要写“时刻未记录”。不因缺少钟点跳过该目标，也不填写 `00:00:00` 或补录执行时间。

### AC-013｜历史背景不计入指定日期

**给定**：当前会话在指定日期引用了旧文档、以前的工作总结或旧实现，用来解释当前问题，但这些旧工作不是该日发生的。

**预期**：旧工作不形成该日工作记录，也不被写成该日重新完成。

### AC-014｜按指定项目过滤

**给定**：用户指定单一项目，当前可见会话同时包含该项目的目标、另一个项目的明确目标，以及项目归属不明的事项。

**预期**：只记录明确属于指定项目的目标。另一个项目不写入。归属不明的事项不归类，并在报告中说明。

### AC-015｜不扫描其他会话或项目

**给定**：用户要求补录指定日期，并说“包括今天的全部工作”。当前可见会话之外还有其他聊天和项目文件。

**预期**：只使用当前可见上下文、本次明确提供的材料和该日已有受管工作记录。不打开其他会话，不遍历项目寻找证据。

### AC-016｜缺少完成证据时不升级

**给定**：指定日期的一个目标只有分析结论、方案或提示词修改，没有实现、验证或用户确认。

**预期**：可以写工作记录，但状态不得为 `COMPLETED`；正文写明证据缺口，不用“无”占位。

### AC-017｜补录后不自动生成日报

**给定**：批量补录已经写出一份或多份工作记录。

**预期**：报告新建、复用和跳过项后停止。不创建或更新日报、周报。

### AC-018｜目标对应关系有歧义时不覆盖

**给定**：一个新识别目标可能对应两条已有记录，或两个目标都可能对应同一条已有记录。

**预期**：不更新、不覆盖、不另建竞争记录；相关已有文件保持原样；报告为待确认。

### AC-019｜记录当前任务仍是单目标

**给定**：用户明确调用“记录当前任务”。当前可见会话里除当前目标外还有其他独立工作。

**预期**：只处理当前这一个工作目标。不批量补录其余目标，也不把整个会话合成一条记录。

## 10. 已采用假设

- 首版运行环境是 Codex；其他 AI 只可能通过用户提供的 Markdown 或会话导出材料参与，不承诺平台集成；
- 用户通过明确调用启动每个动作，不自动触发写入；
- 当前项目根目录可以由 Codex 可靠识别；无法识别时由用户指定；
- 用户明确指定的目录就是最终 `work_summary_root`，不再自动追加一层 `work-summary/`；
- 未指定目录时才使用 `<当前项目根目录>/work-summary/`；
- 时区为 `Asia/Shanghai`，周一为每周第一天；
- 工作记录使用 UUIDv7，并增加 `wrk_` 前缀；
- 日报和周报采用“整个 AI 区域可重新生成，人工区域独立保护”的模式；
- 日报默认面向个人复盘，同时保持可复制为工作汇报的正式表达；
- 同一工作目标可以由 AI 提议归并，但存在实质歧义时需要用户确认；
- 首版只管理采用本契约标记协议创建的文件，不自动迁移历史报告；
- Markdown 使用 UTF-8 保存。

## 11. 已知限制

- 当前需求材料没有保存真实验证的样本明细和量化结果，开发后仍需使用真实样例完成行为验证；
- UUIDv7 只能稳定标识记录，不能自动证明不同记录属于同一工作目标；
- 当前会话未必提供稳定、可读取的会话 ID，更新记录仍可能需要用户提供路径或 `work_id`；
- AI 对跨会话工作目标的归并可能出现误判；
- 用户在 `AI-MANAGED` 区域进行的人工修改可能在下一次生成时被覆盖；
- HTML 注释边界需要在实际 Codex 和 Markdown/Obsidian 使用环境中验证；
- 首版没有后台定时、并发写入、锁、数据库或跨设备同步；
- 不符合本契约结构的历史日报和周报需要人工决定是否迁移。

## 12. 仍需人工决定的问题

以下问题不改变本契约的主体行为，但应在创建或验收前明确：

1. 是否需要在首版验收中加入一组真实历史日报的只读兼容测试；默认只测试，不迁移、不覆盖。
2. 是否将某个集中归档目录作为个人常用调用参数；默认不硬编码全局绝对路径。

## 13. 契约通过条件

只有同时满足以下条件，本契约才可以进入 Create：

- 用户确认目标、非目标和显式调用边界；
- 用户确认动态目录解析规则；
- 用户确认目录、命名、UUIDv7 和跨月周归档规则；
- 用户确认 AI 托管区和人工区域的覆盖边界；
- 用户确认读取、写入、外发和停止条件；
- 正式 Skill 名称和显式调用名称与本契约一致；
- 没有仍会改变核心行为、授权边界或验收结果的冲突。

## 14. 契约修订记录

### REV-L-001｜默认界面文案和报告骨架语言

- 原有规则：契约正文和报告内容要求主要使用中文表达，但没有明确规定用户可见界面文案及工作记录、日报、周报骨架的默认语言；
- 修订后规则：上述用户可见内容默认使用简体中文，机器可识别的既有英文标识保持不变；
- 修改理由：原始需求、目标使用场景、报告栏目和现有契约均以中文为主要表达语言，明确默认值可以避免实现时出现中英文混排，同时不改变调用、读取、写入、外发、确认或验收边界。

### REV-M-002｜正式 Skill 名称和显式调用名称

- 原有规则：正式名称尚未确定，契约仅建议使用 `work-summary` 或 `ai-work-summary`，并将名称确定列为契约通过条件；
- 修订后规则：正式 Skill 名称和显式调用名称确定为 `ai-work-summary-skill`；
- 修改理由：现有 Skill 元数据和默认显式调用提示已经一致使用 `ai-work-summary-skill`，原始需求没有规定相冲突的调用名称；确认现名可以消除契约与实际对象之间的不一致，且不改变目标、范围、调用策略、权限或验收标准。

### REV-L-002｜契约确认状态

- 原有规则：契约状态为“待人工确认”；
- 修订后规则：契约状态更新为“已人工确认”；
- 修改理由：用户已明确确认处理 `REV-L-002`；现有契约与原始需求中已确认的产品决定不存在阻止确认的冲突。本次修订只更新流程状态，不改变目标、范围、调用策略、权限、停止条件或验收标准。

### UX-001｜机器字段与中文展示分层

- 原有规则：机器字段使用英文枚举、UUIDv7 和带时区时间，但正文没有强制提供与其一致的中文可读摘要，工作记录标题也可能退化为纯 `work_id`；
- 修订后规则：保留现有机器字段格式和稳定 ID，在 AI 托管正文中增加由 YAML 派生的中文摘要，并要求使用有实际含义的中文标题；
- 修改理由：机器层必须继续满足校验、去重、排序、时区和跨工具交换，展示层则解决 Obsidian 中阅读英文枚举、RFC 3339 和纯 ID 标题不直观的问题。分层避免引入全局顺序号、重复标签字段和两套相互漂移的数据。

### REV-M-003｜增加指定日期的可见会话批量补录

- 原有规则：显式动作只有记录当前任务、生成或更新日报、生成或更新周报；
- 修订后规则：增加第四个显式动作“按指定日期批量补录当前可见会话中的工作记录”。它按独立工作目标写入普通工作记录，只读取当前可见会话、本次明确材料和该日已有受管记录，并用可靠的目标对应关系去重。它不改变前三个动作，不新增文档字段，也不自动生成日报；
- 修改理由：现有“记录当前任务”只稳定覆盖一个当前目标。把同一会话中的多个目标交给它，会合成一条记录或误走日报。单独的动作边界可以复用既有写入协议，同时堵住历史引用误计、模糊合并和其他会话扫描。

### REV-L-004｜缺少发生时刻时仍保留工作记录

- 原有规则：指定日期可靠但没有可支撑的钟点时，批量补录不建记录；
- 修订后规则：日期可靠时仍然写入工作记录，并省略 `time`。记录摘要写“时刻未记录”。只有日历日期本身无法判断时才跳过。不得用 `00:00:00` 或补录执行时间充当时刻；
- 修改理由：缺少钟点只说明发生时刻不明，不说明这件工作没有发生。整条跳过会造成事项遗漏。`time` 改为可省略后，机器层不必保存一个虚构钟点。

### REV-L-005｜用日期指定周报周期

- 原有规则：周报按 ISO 周保存，调用示例直接使用 `2026-W40` 这类周编号；
- 修订后规则：用户用一个日期指定周报。该日期所在的周一至周日由 `paths` 解析，文件仍使用原来的 `week_id` 和起止日期。用户不需要自己计算周编号；
- 修改理由：调用时用户能确定的是某一天，不是 `YYYY-Www`。周编号继续留在文件里供校验和追溯。
